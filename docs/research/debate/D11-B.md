# D11-B: against LLM-authored scene code as the default backbone

## Thesis
Keep a small set of human-written, parametrized templates (stat, code, diagram, timeline, comparison) filled by the LLM with JSON only, plus the curated figure library. Use LLM-written code only as an opt-in "hero" path. The proposition buys flexibility the channel does not yet need, at the price of cost, security and QA risk. The channel has no proof of demand.

## Arguments
1. **Cost is unmeasured and eats the cap.** The addendum's own estimate is $1.2-1.8 per long video (11-addendum, section 3), explicitly "not measured". Pricing confirms Sonnet 5.5 at $2/$10 per MTok (https://platform.claude.com/docs/en/about-claude/pricing). At $1.2-1.8 x 8 videos, that is $10-14/month. Plan section 3 budgeted about $9 total for all LLM work, and the internal cap is $25 with a $1.50 per-run cap (Plan.md, Global Constraints). Under this proposal the per-run cap must be raised, so every other failure (Shorts, retries, claim check) now hits the cap. A template path costs only JSON fill-in, roughly the script cost already budgeted.
2. **Generated code is brittle.** Each repair resends the code and the errors. Manim also needs a heavy toolchain (Cairo, ffmpeg, LaTeX). Its install page lists no Windows notes (https://docs.manim.community/en/stable/installation.html). The addendum itself marks Manim on this PC as UNVERIFIED (Spike E, section 6). Failure after 2 repairs falls back to stock B-roll, so the "default" backbone degrades silently into the generic visuals the plan wants to avoid.
3. **Executing LLM-written code is a security surface.** The plan's own Review Focus item 5 (Plan.md) names LLM text injected into sinks. Here the LLM writes Python that runs locally. The mitigation (patch 4: subprocess, timeout, "no network") is not specified for Windows, which has no easy network-off sandbox. Source text arrives from scraped web pages, so prompt injection can reach code execution. This is my inference, not a sourced incident. Templates have no such surface.
4. **Vision QA is unproven.** Three sampled frames cannot catch overlap or timing errors between frames, or wrong sync. No accuracy figure for Haiku on clipped-text detection exists in any file (UNVERIFIED). A cheap deterministic check (DOM `getBoundingClientRect` overflow test on HTML scenes) beats a model for clipping.
5. **It does not clearly reduce the policy risk.** YouTube's text says "the substance of each video should be materially varied" and targets content "made with a template" (https://support.google.com/youtube/answer/1311392). Varied visuals do not equal varied substance. LLM scene code that converges on the same layouts, with the same prompt, is still templated, and nobody has audited it. Fixed human-designed templates with real varied data and sources are no worse.

## Strongest point FOR, and my answer
It fixes G1 and G2: reveals timed to `words.json`, with a variety that a fixed library cannot supply. Answer: templates can consume `words.json` cues as parameters (reveal order and times), so sync does not need generated code. Variety comes from 6-10 templates plus topic data.

## What would change my mind
A Task 16 pilot of 5 videos showing average cost under $0.80, first-pass render success of 85% or more, a Manim run on this PC, and a labeled test where the vision QA catches 90% of clipped slides.

## Scores (templates plus library, deterministic)
- Cost: 5
- Output quality: 3
- Policy risk: 3
- Implementation effort: 4
- Maintainability: 4
